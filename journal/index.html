Identity & Access · Azure

Nothing to Steal

An attacker has the code, the configuration and a shell on the server. A zero-trust lab on Azure was built to answer one question — what can they take? — and to keep the evidence of the answer.

By Sai Vignesh RayalLab run of October 28, 2026 · azure-iam-zero-trust-lab

The usual way to give an application a secret is to give it another secret: a connection string, a client key, a token in an environment variable. Each one is a credential that can be copied. The lab starts from the opposite premise. The workload holds no reusable credential at all. It proves who it is through a managed identity, and Azure hands it a short-lived token in return.

That identity has exactly one role assignment — Key Vault Secrets User — scoped not to the vault but to a single secret. A second secret sits beside it in the same vault, a decoy belonging to an imaginary other team. If the boundary is real, reading the decoy must fail.

If the boundary is real, reading the decoy must fail. It does — and the log records the attempt.Fig. 2, the box score

The vault itself refuses network traffic by default. Its firewall denies everything, the trusted-service bypass is off, legacy access policies are gone, and purge protection means a compromised administrator cannot quietly destroy it. Each of those settings is checked by a script after deployment, not by eye; on October 28 every check passed.

Delivery without a secret

Deployment follows the same rule. The pipeline authenticates to Azure through GitHub's OIDC federation, so there is no client secret to leak from the repository, and an attribute-based condition limits the one role the pipeline may grant. Before anything deploys, the build compiles the template and runs 31 tests against it, lints it with security rules treated as errors, scans it with Checkov and searches the entire git history for secrets.

Breaking it on purpose

The lab then attacks itself. Eight adversary-emulation scenarios — among them an insider asking for the machine's token, a hunt for credentials on disk and in memory, server-side request forgery against the identity endpoint, and root on the box — run against a hardened Ubuntu server joined to Azure through Arc.

Not every result was clean, and the write-up says so. A stolen token replayed from the same home network still worked. It is recorded as RISK-08, accepted, and covered by detection rather than prevention. The absence of a private endpoint and of Privileged Identity Management are documented the same way: the residual risk, the compensating control, and the paid upgrade that would close it.

Proof that outlasts the demo

What remains is evidence. Every file from the October 28 run is redacted, hashed with SHA-256 and listed in a checksum manifest. Each of 29 NIST SP 800-53 controls is traced to its implementation, the test that exercises it, the evidence that test produced and the threat it answers — and a test fails the build if a threat ever loses its control.

Network · AWS

A Range With No Way Out

Before a single vulnerable machine exists, a cyber range has to prove it cannot reach the internet. So the tests come first.

By Sai Vignesh Rayalliving-museum-of-cyber-warfare · release pending

A practice range for attack and defence has an obvious failure mode: the thing being studied gets out. The Living Museum of Cyber Warfare — a lab for studying historical attacks, protocols and detection — is built so that it cannot. Its rule is written into the repository: no vulnerable machine or exploit scenario is deployed until the guardrail tests pass.

The network is an AWS VPC with four subnets — management, sensor, lab and quarantine — and no path out. There is no internet gateway, no NAT gateway and no elastic IP, and no subnet assigns public addresses. Network ACLs admit only traffic that starts and ends inside the VPC; the quarantine subnet may speak only to the sensors. Management runs through Systems Manager endpoints inside the VPC, so there is no bastion to harden and no port to open.

Every packet accounted for

VPC flow logs capture all traffic into a CloudWatch log group encrypted with a rotating key. Security groups are written by role — attacker, target, sensor — and none references 0.0.0.0/0.

Guardrails that execute

A static check fails the build if any configuration so much as declares an internet gateway, a NAT gateway, an elastic IP, a public address or an open CIDR. Terraform's own test framework then plans the network against a mock provider and asserts that the quarantine and sensor subnets exist and that flow logs capture everything. By default the configuration creates nothing at all; the network is built only when it is deliberately switched on.

Next on the bench: the sensors themselves — Zeek and Suricata, fed by VPC traffic mirroring from the lab subnet.

Opinion

Evidence Is the Product

Sai Vignesh RayalColumn

Security work is easy to describe and hard to prove. "Access is least-privilege" is a sentence; a role-assignment export scoped to one secret is a fact. Much of my work in cloud security and compliance has been the patient conversion of the first kind of statement into the second.

The chain is short: a control, the test that exercises it, the evidence that test produces, and a hash showing the evidence has not changed since. When a link is missing, the claim is a hope. When all four are present, an assessor can follow the claim without taking anyone's word for it — mine included.

That is why the open items are published beside the finished ones. A control register with no gaps has usually not been read closely. Mine lists five, each with an ID. When they close, the evidence will say so.
